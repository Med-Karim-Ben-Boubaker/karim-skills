# Discovery

**You own the map, not the decision.** The user often doesn't know the domain yet: explore and explain, don't interrogate. There is no fixed order. Pick the tool that fits each open question, and repeat until the user has what they need.

1. **Write the open questions.** *Done when:* a short list of what we don't know yet is in your todo list.
2. **Answer each with the tool that fits.** *Done when:* every question is answered, or marked with who can answer it.

   | The question needs | Tool |
   |---|---|
   | Facts from documents, standards, APIs, or prior records | the "research" skill |
   | Running something to see if it holds up | the **prototype** playbook |
   | Names and rules the team should share | the "domain-modeling" skill |
   | An answer only the client or an expert has | the "to-questionnaire" skill |
   | Stress-testing a view the user already holds | the "grilling" skill |

3. **Write it down.** Findings live in the repo: `research/`, `GLOSSARY.md`, `docs/adr/`, `prototype/<slug>` branches. *Done when:* each answer points to a file, not only to the chat.

**Reply:** what we now know with links to the files, what is still open and who can answer it, and which playbook fits next (usually **planning**).
